chromatika - send flow diagrams

from "send" button to on-chain confirmation. on the sui ika base path (production), every dWallet signature - regardless of destination chain - is produced by ika MPC running on the sui chain. the three-step ika block is identical across all destination chains; only the presign pool and hash scheme differ.

step (2) signer varies per vault type - HD vaults sign with the mnemonic-derived sui keypair, hardware vaults sign on-device, passkey vaults sign via WebAuthn UV, etc. see the per-vault-type table at the bottom for who signs and who pays.

on the solana ika base path (pre-alpha, dev-mode mock signing), the architecture is different: no sui PTB, instead a Solana anchor program approve_message + ika gRPC Sign. covered in its own card below the sui-base flows.

▼ solana-base ika - gRPC + anchor program (no sui PTB)
①
ika gRPC + solana
presign (varies by curve)
SECP256K1: pool-take from SECP256K1_ECDSA just like sui base - solana ika supports PresignForDWallet over gRPC for ECDSA, refilled by background alarm.
ED25519: never pools. RFC 8032 deterministic + pre-alpha gRPC PresignForDWallet rejects Curve25519 ("PresignForDWallet is only for imported ECDSA keys"). Instead, every Sign does a fresh per-call requestPresign(curve, sigAlg) over the global DWalletRequest::Presign variant.
🔑 fee-payer keypair (ikaGrpcFeePayerSolSecretKeyB64 on the hardware vault record, or the Lazor lazorIkaFeePayerSolSecretKeyB64) pays the gRPC fee · funded with ~0.1 devnet SOL after vault create
②
ika gRPC + solana
approve_message + Sign
chromatika-policy Solana anchor program do_approve_message_cpi (currently a stub until ika alpha 1 ships the CPI target) → ika gRPC Sign with the approved message + presign reference. Mock signer returns a single signature (NOT distributed MPC).
curve: SECP256K1 / ED25519 · hash scheme per chain · scheme: signature_scheme = Secp256k1 or EdDSA
🤖 step (1) presign + step (2) approve_message both signed by the in-extension fee-payer keypair (solanaFeeKeypairFromWalletSignature(signature, 1) for MWA / WC / Seeker; SLIP10-derived for Lazor). Same Seeker on any device produces the same fee-payer address.
③
ika gRPC + solana
poll for Sign output
gRPC poll for Completed state · returns signature bytes (mock signer output, single signature)
⚡ devnet wipes can drop dWallet state - operation-progress banner surfaces a "recreate dWallet" recovery action via DWalletGoneError when the gRPC returns "no key for dwallet ... or scheme X incompatible with curve Y"
📡 gRPC poll · zero on-chain solana cost (no anchor tx for the polling itself)

🚨 solana ika base is dev-mode mock signing. the disclaimers in the root README and on every solana-ika UI surface apply: signatures are produced by a single mock signer, not distributed MPC; the ika program + on-chain data will be wiped at alpha 1; the dWallet keys, trust model, and signing protocol are not final. do not submit real-value transactions on this stack. only flip VITE_SOLANA_IKA_BASE=true in dev builds.
🔑 the sui-base ika MPC block is identical on every destination chain - what changes is pool + hash
steps ①②③ are always: draw presign id from pool → build & execute IkaTransaction PTB on the sui chain → poll getSignInParticularState('Completed'). the service worker never holds the raw private key - only the encrypted user share id.

🤖 step (2) signer + payer varies per vault type. the table below lists who signs the on-chain sui PTB at step (2) and who pays the SUI + IKA + sui-network gas. presigns are pre-created in the background by the same signer, refilled every 5 min by a chrome.alarms job (low-water 2 per pool, refill count 3). step (3) is a read-only RPC poll - no gas, no transaction.
vault type step (2) signer who pays SUI + IKA gas notes
HD (mnemonic) BIP44-derived sui keypair at m/44'/784'/0'/0'/{idx}', in session memory same keypair (sui address) auto-signed in the background, no user prompt per send
imported privkey (sui) imported suiprivkey... Ed25519 keypair, in session memory same keypair auto-signed; same shape as HD
passkey (sui) WebAuthn user-verification on the passkey credential (no hot key) passkey-derived sui address (sip-9 scheme) user verifies on the authenticator per send (touch / biometric); no extension-resident secret
WaaP (sui) WaaP-managed sui keypair, signed via @human.tech/waap-sdk API WaaP-managed sui address off-device signing per send; no extension-resident secret
Ledger (sui) Ledger sui app on-device, via WebHID popup Ledger-derived sui address (hardwareAccountId) opens ?hwsign=ID popup per send; user approves on Ledger device. legacy suiPrivateKeyBech32 fallback exists for old dev installs (tech debt; goal is Ledger-only)
dWallet-anchored anchor dWallet's resolved owner sui keypair (mnemonic / privkey) resolved owner address same shape as the underlying owner record
↓ solana base vaults skip the sui PTB entirely (see solana ika base card above) ↓
HD (solana base) SLIP10 solana keypair at m/44'/501'/{idx}'/0' same keypair (pays gRPC approve_message fee in devnet SOL) no sui PTB - gRPC + anchor program flow per the solana ika card above
imported privkey (solana) imported 64-byte solana keypair same keypair same shape as HD solana
Lazor (solana base) SLIP10-derived lazorIkaFeePayerSolSecretKeyB64 (separate from the smart-wallet PDA) fee-payer address (~0.01 devnet SOL) passkey at lazor portal authorizes the smart wallet itself; chromatika-side fee payer is a separate keypair derived from the recovery phrase
MWA local / remote (Seeker) deterministic solanaFeeKeypairFromWalletSignature(signature, 1) from Seeker's signature over IKA_USK_DERIVATION_MESSAGE fee-payer address (~0.1 devnet SOL); same Seeker on any device = same address Seed Vault on phone signs every chain transaction; fee-payer keypair only signs ika gRPC fees
WalletConnect (solana) same deterministic fee-payer keypair as MWA when WC wallet supports solana_signMessage over IKA_USK_DERIVATION_MESSAGE; otherwise recovery-words fallback fee-payer address canonical desktop solana hardware path today (Solana Mobile reflector is currently unreliable)
⛽ gas per send (step 2): dynamic per call via getRequiredCoinAmounts(ikaClient) (reads coordinatorInner.pricing_and_fee_manager.current.pricing_map with a 10% buffer) + sui network gas (~0.005-0.02 SUI). never hardcoded - the on-chain pricing changes and chromatika queries it per send. BTC sends with N UTXO inputs execute N separate (2) PTBs - total cost scales linearly. presign pre-creation (background) carries the same per-presign structure. requireSuiAndIkaCoins() confirms the fee payer holds both coin objects before any PTB is attempted.

what varies per destination chain (sui-base): which pool (SECP256K1_ECDSA / SECP256K1_TAPROOT / ED25519_EDDSA), which hash scheme (keccak256 / doubleSHA256 / SHA-512), and whether v recovery is needed (ECDSA-based chains like EVM need it; EdDSA-based chains like Solana and Sui don't). the IkaTransaction PTB always executes on sui regardless of destination chain.
