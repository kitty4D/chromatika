# Chromatika status

Single index of what's shipped, gated, stubbed, and planned. Updated when the code reality changes. Other docs (architecture-final.html, WALLET_SECURITY.md, DWALLET_VAULT_MODEL.md) point here instead of duplicating status.

Pre-release: chromatika has not shipped to end users. Storage/crypto are dev-only; schema breaks allowed without migrations.

---

## Shipped (in main, usable today)

### Core
- **Vault** - Argon2id (RFC 9106 §4 second option: t=3, m=64 MiB, p=4) + AES-256-GCM, multi-record `chromatika_vault_v3` with per-vault `dwalletMeta` overlay (`chromatika_dwallet_meta_v2_<vaultId>`). Session holds non-extractable AES `CryptoKey` (no password string in RAM). Unlock cache holds derived key bytes (b64) + KDF meta in `chrome.storage.session` only - never the plaintext password.
- **Keyring** - BIP39/44, SLIP10 ed25519, dWallet ed25519 public-key derivation.
- **Auto-lock** - `chrome.idle` + `chrome.alarms`; OS screen-lock triggers wallet lock.
- **Phishing** - dNR dynamic rules (<5000 cap), bundled list + daily refetch of MetaMask `eth-phishing-detect`.

### Ika (Sui base)
- dWallet DKG / presign pool / sign / re-encrypt, three presign pools (`SECP256K1_ECDSA`, `SECP256K1_TAPROOT`, `ED25519_EDDSA`), per-vault presign store, 5-min refill alarm.
- `IkaClient` runs on the vault `SuiGraphQLClient` (`client.core.*`), never JSON-RPC for supported paths.
- Dynamic pricing via `getRequiredCoinAmounts`.
- Sui testnet + Ika testnet usability audit (faucets, hardcoded-mainnet edge cases, pre-flight checklist): [`IKA_SUI_TESTNET_AUDIT.md`](IKA_SUI_TESTNET_AUDIT.md).

### Chain clients
- **EVM** - ethers v6; `eth_sendTransaction` dapp flow (approval popup) + wallet-UI `sendEvmTx` (no popup). Keccak preimage passthrough for `personal_sign` and `eth_signTypedData_v4`.
- **Bitcoin** - bitcoinjs-lib, segwit + taproot sends.
- **Solana** - `@solana/web3.js`, send + off-chain message signing.
- **Sui** - `@mysten/sui` 2.16.0 (pinned via `pnpm.overrides`), GraphQL only (no JSON-RPC), `IkaTransaction` flows.
- **Aptos** - `@aptos-labs/ts-sdk`.

### UI surfaces (`src/ui/pages/`)
- Assets, Activity, Send, Portfolio, DWalletPortfolio, NFTs, DApps, IkaStaking, NetworkSelector, Settings, Vault/DWallet management, ChromaLab (dev), Wallet. Kiosk management lives as a panel inside NftsPage.

### Dapp bridge
- EIP-1193 / EIP-6963 (including 3085/3326), `window.bitcoin`, `window.aptos`, Wallet Standard for Sui + Solana.
- Sui transactions sign via Mysten intent + BLAKE2b (`signBuiltSuiTransactionBytes`).
- `sui_signPersonalMessage` produces Mysten-standard signatures: BCS-encodes the message as `vector<u8>`, prepends the PersonalMessage intent (`[3,0,0]`), BLAKE2b-256 hashes, then signs the digest via the ika ed25519 MPC path. Verified byte-for-byte compatible with `@mysten/sui` `Ed25519Keypair.signPersonalMessage` + `verifyPersonalMessageSignature` (see `chains/sui-personal-message.test.ts`). Unblocks Sui dapps that use `verifyPersonalMessageSignature` (most of them) AND the future Seal backend's SessionKey flow.
- **x402 fetch interception** - `dapp-interface/x402-fetch-wrapper.ts` wraps `window.fetch` so any page response with `HTTP 402 + PAYMENT-REQUIRED` is automatically routed through the wallet's approval popup, signed, and retried with `PAYMENT-SIGNATURE`. See the "x402" section below for details.
- New dapp-bridge methods on the existing port: `chromatika_x402_handle_402` and `chromatika_x402_record_settlement` route 402s through the wallet without any new transport.

### Data services
- **Price waterfall** - CoinGecko → DefiLlama → CoinMarketCap (requires `VITE_CMC_API_KEY`) → Pyth → Chainlink (EVM proxy feeds) → GeckoTerminal DEX TWAP (IKA). ~60s cache.
- **NFT services** - Sui (on-chain + Display), Bitcoin (Hiro Ordinals), EVM (Alchemy, needs `VITE_ALCHEMY_KEY` or returns empty), Solana (Helius DAS, needs `VITE_HELIUS_KEY` or returns empty), Aptos (Token v2 indexer).
- **Kiosk** - `@mysten/kiosk` `KioskClient` (owned/managed, listings, transfer policies, royalties).
- **MediaSafetyMode** - `all` / `ipfs-arweave` (default) / `none`. Enforcement is in-request only; no cache layer.

### Hardware
- **Ledger** - WebHID in popup/side-panel context, never in the SW. EVM (`personal_sign`, tx, EIP-712), Sui (`suiTx`), Solana (tx, off-chain), Bitcoin (PSBT via `hw-app-btc@10.x` `signPsbtBuffer`, bech32 + legacy paths). Sui app/firmware floors in `LEDGER_SUI_LIMITS.md`.
- **Trezor** - account discovery + EVM message/typedData + Solana tx signing + **Bitcoin (BIP84 P2WPKH) via `TrezorConnect.signTransaction` + PSBT decomposition** through `btc-trezor-decompose.ts` (parses PSBT → `TxInputType[]` / `TxOutputType[]` with change detection + Esplora-fetched `RefTransaction[]`). Live device round-trip is a manual smoke (no hardware in CI); parser is unit-tested. CSP adds `frame-src https://connect.trezor.io`. Sui not supported by Trezor Connect.
- **Solana Mobile Wallet Adapter (MWA)** - **two transports** for Solana hardware-wallet onboarding, dispatched on `mwaTransport` carried through `HardwareVaultRecord` → `SessionState.solanaMwaAccount` → `PendingHardwareSign`:
  - **Local (Android Chrome)** - `@solana-mobile/mobile-wallet-adapter-protocol-web3js` `transact()` launches the mobile wallet via Android intent on the same device; `vendor:'mwa', mwaTransport:'local'`. `MwaConnect` registers the phone; `MwaSigner` handles the approval popup. Shown only when UA is Android.
  - **Remote (desktop ↔ Seeker / phone, QR pair)** - `startRemoteScenario()` opens `wss://reflect.solanamobile.com` from the side panel / popup (cannot run in the SW because the lib touches `window.btoa`/`atob`), renders an association URL as a QR; user scans with the Seeker camera (or any MWA-compliant phone wallet "scan link" input) and approves in Seed Vault. Persisted `auth_token` + `reflectorHost` let every subsequent sign reauthorize without rescanning the QR; `ERROR_AUTHORIZATION_FAILED` surfaces a re-pair prompt. `vendor:'mwa', mwaTransport:'remote'`. `SeekerConnect` runs the QR flow; `MwaSigner` dispatches local-vs-remote on `mwaTransport`. Shown only when UA is **not** Android. Solana-only.
  - Because Seed Vault never exposes secret bytes, MWA + Solana base vaults derive an **in-extension Solana fee-payer keypair deterministically from the wallet's signature** over `IKA_USK_DERIVATION_MESSAGE` at index 1 (`solanaFeeKeypairFromWalletSignature(signature, 1)`, persisted as `ikaGrpcFeePayerSolSecretKeyB64`). Same Seeker / same phone wallet on any device produces the same fee-payer address, so SOL persists across reinstalls. The ika `UserShareEncryptionKeys` seed comes from the same wallet signature at index 0 (`ikaRootSeedFromMwaSignature`); the fee-payer derivation uses index 1 to avoid collision. The Seed Vault on the phone still signs every chain transaction (sends, dapp signing, dWallet authorize). No companion vault is required. Old dev installs may carry the deprecated random `ikaEncryptionOnlySolSecretKeyB64` field as a read-fallback only (no new writes). **MWA-remote is `false` by default in prod builds (`VITE_ENABLE_MWA_REMOTE=false`)** because Solana Mobile's reflector demo is currently unreliable; WalletConnect is the canonical Solana hardware path on desktop today.

### Agents (MCP)
- **Native messaging host** - `wallet-extension/native-host/chromatika-mcp-host.mjs` (zero-deps node script). Two invocation modes:
  - default: chrome-spawned host, hosts `POST /mcp` HTTP MCP transport on `127.0.0.1:<port>` with bearer-token auth, forwards `tools/list` + `tools/call` to the extension via native messaging stdio.
  - `--stdio-bridge`: child-process spawned by stdio MCP clients (Claude Desktop default), forwards line-delimited JSON-RPC to the chrome-spawned host via env-var-configured URL + token. Lets clients that don't speak HTTP MCP drive the wallet.
  - Setup: `pnpm setup:native-host --extension-id=<id>` registers the host on the user's OS (per-OS native messaging directory + Windows `.bat` shim + `reg add`).
- **Bridge** - `src/background/mcp/mcp-native-bridge.ts` connects via `chrome.runtime.connectNative`, capped exp backoff (5 attempts, 1s→30s), pushes per-install token + desired-port to host on connect. Re-establishes on SW startup if surface is enabled.
- **Read tier (no popup)** - `listVaults`, `getActiveVault`, `getActiveNetworks`, `getLockState`. Wraps existing wallet-service / network registry / session APIs.
- **Approve tier (popup-gated)**:
  - `signMessage` ({ chain: 'evm' | 'solana', messageHex, evmChainId? }) → `McpApprovalScreen` popup → ika MPC signs → returns `{ chain, signatureHex, signerAddress }`.
  - `sendEvmTx` ({ to, value?, data?, chainId?, gas?, ... }) → existing `ApproveTxScreen` popup with full gas/sim UI → `signAndBroadcastEvm` → returns the broadcast txHash.
  - `signTransaction` ({ to, value?, data?, chainId?, gas?, ... }) → same popup with "sign only — no broadcast" banner → `signEvmTxOnly` → returns `{ signedRawTx, txHash }` for relayer / bundler / abstract-wallet flows.
- **Settings UI** - `AgentsSettingsSection` enables/disables the surface, shows per-install bearer token (reveal/copy/rotate), agent URL, native-host status, optional fixed listen port (1024-65535) for stable Claude Desktop config across chrome restarts. Per-port rebind is handled by the host on `{ type: 'reconfigure-port' }` with fall-back to the random port on bind failure.

### Trezor BTC PSBT decomposition (2026-05-02)
- **Implemented** the `TrezorSigner.tsx` `btcTx` branch (previously threw "use Ledger for Bitcoin"). New module `src/background/chains/btc-trezor-decompose.ts` does the PSBT → Trezor `signTransaction` shape conversion: parses the PSBT, builds `inputs: TxInputType[]` with `script_type` detection (P2WPKH / P2SH-P2WPKH / legacy), `outputs: TxOutputType[]` with change-address detection (own `address_n` vs external `address`), and a list of `refTxIds` for Esplora prev-tx fetching.
- **`fetchAndDecodeRefTxs(refTxIds, esploraBase)`**: pulls each prev tx hex from Esplora `/tx/<hash>/hex` and decodes into Trezor's `RefTransaction` shape (bin_outputs variant) so the device can verify input values by hashing the prev tx and matching `prev_hash`. Sequential fetches (≤10 inputs typical for chromatika sends) to be polite to public Esplora endpoints.
- **`PendingHardwareSign` extended** with `bitcoinNetworkId?: 'btc-mainnet' | 'btc-testnet'` and `bitcoinEsploraBase?: string`. Trezor signer requires both for the `btcTx` path; Ledger ignores them (signPsbtBuffer is network-aware internally) but `btc-send-native.ts` populates them on every BTC enqueue for uniform meta records.
- **Tests**: 21 cases at `btc-trezor-decompose.test.ts` — `parseBip44PathToNumbers` (BIP84 hardened, plain numbers, `m/` prefix stripping, hardened markers, error paths), `detectInputScriptType` / `detectOutputScriptType` (P2WPKH / P2WSH / P2SH-P2WPKH / legacy), `bytesToHexBe` (display-order reversal), `decomposeBtcPsbtForTrezor` end-to-end (1-input/2-output testnet + mainnet coin string + missing witnessUtxo throw + external-only outputs when no changePath), `decodeRawTxToRefTransaction` (raw tx hex → Trezor refTx shape).
- **End-to-end status**: parser validated, signer wired. Live `TrezorConnect.signTransaction` round-trip (sign + broadcast) requires real Trezor hardware on regtest/testnet — documented as a manual smoke; the path is no longer a stub. ### Encrypt-label auto-rebuild after devnet wipe (2026-05-02)
- **Problem**: Encrypt devnet rotates periodically per disclaimer; existing `encryptedLabel.ciphertextIdentifierHexes` accounts disappear; reveal returns "missing on-chain" and the user has to clear + re-encrypt manually each time.
- **Solution**: opt-in plaintext cache + automatic re-encrypt. Toggle storage key `chromatika_label_auto_rebuild_v1` (default OFF; opt-in). When ON, `createDwalletLabelCiphertext` stashes the plaintext in `encryptedLabel.cachedPlaintext`. The poll-driven on-chain status check (`getDwalletEncryptedLabelOnChainStatus` returns `'missing'` after a wipe) triggers `rebuildDwalletLabelAfterDevnetWipe(curve)` which re-runs the encrypt with the cached plaintext + rotates `ciphertextIdentifierHexes` in place. `createdAtMs` stamps fresh; UI shows "rebuilt N min ago" pill.
- **Security boundary**: lab-grade pre-alpha labels are explicitly NOT for secrets (per the encrypt program disclaimer); locally caching the plaintext is consistent with that boundary. Toggle is opt-in so users who want the strictest behavior keep "no plaintext on disk" by leaving it off (and lose the auto-recovery in exchange).
- **UI**: `DwalletEncryptedLabel.tsx` gets a "auto-rebuild after devnet wipe" checkbox (toggle in widget itself, not Settings). When the on-chain status flips to `missing`, the action button switches from "reveal" (disabled) to "rebuild" — manual fallback when the toggle is off but a cached plaintext exists from a prior session. Auto-trigger fires once per "missing" run when the toggle is on.
- **tRPC**: `getEncryptedLabelAutoRebuildEnabled`, `setEncryptedLabelAutoRebuildEnabled`, `rebuildDwalletLabelAfterDevnetWipe(curve)`. Throws when no `cachedPlaintext` is stored.

### DeSo binary hard-decoder in Move (2026-05-02)
- **Move-side**: new `chromatika_policy::sign_gate_deso` module at `move/chromatika-policy/sources/sign_gate_deso.move`. Decodes the v0 DeSo binary tx layout (per deso-protocol/deso-js transaction-transcoders.ts spec): `varint(input-count) || N×(TxID[32] + uvarint(Index)) || varint(output-count) || N×(PublicKey[33] + uvarint(AmountNanos)) || metadata || pubkey || extra || sig`. Skips inputs, sums all output AmountNanos, returns `(output_sum_nanos, largest_output_nanos, output_count)`. New `sign_deso_with_policy` entry takes a caller-supplied `priceMicrosPerDeso`, computes chain-derived `value_micros = sum * price / 1e9`, emits `DeSoDecoded` event with sum + largest + count for off-chain audit, then delegates to soft `sign_gate::sign_with_policy`.
- **Cap is on SUM of outputs (= input - fee).** Slightly over-conservative because it counts the user's own change against their daily ceiling. Trade-off is "safe and simple" vs "compares pubkeys for change detection." Off-chain auditors can subtract `largest_output_nanos` from `output_sum_nanos` to recover the change going back when needed.
- **Move tests**: 16 cases at `move/chromatika-policy/tests/sign_gate_deso_test.move` — basic 1-input/1-output, typical 1→2 (recipient + change), multi-input UTXO consolidation, zero inputs/outputs, dust amounts, multi-byte varint, max-u64 amounts (saturation), truncated input abort, too-small abort, price-conversion at $30 / $50 / dust / zero / saturation.
- **TS dispatch**: `policy-vault-sign.ts` `PolicySecpSignInput` extended with optional `desoHardPolicy: { priceMicrosPerDeso }`. Four-mode dispatch (EVM hard / BTC hard / DeSo hard / soft) — BTC and DeSo both DoubleSHA256 but mutually exclusive (caller picks one). `deso-send.ts` `signAndSubmitDeSoTransactionHex` now resolves `priceMicrosPerDeso` via `resolveDeSoPriceMicrosPerDeso()` and routes through `signBytesSecpThroughPolicy` directly when in policy mode (preserves the recovery-byte derivation + DeSo DER mutation downstream).
- **Honesty model**: HARD on output-sum (decoded from on-chain bytes); SOFT on price (caller-supplied; emitted on-chain via `DeSoDecoded` event for auditability). Closes the DeSo soft-policy gap from Policy Vault v0.

### BTC PSBT hard-decoder in Move (2026-05-02)
- **Move-side**: new `chromatika_policy::sign_gate_btc` module at `move/chromatika-policy/sources/sign_gate_btc.move`. Decodes the BIP143 witness-v0 sighash preimage (P2WPKH + P2WSH inputs) on-chain in Move; extracts the input UTXO `amount` field at the deterministic offset (PREFIX 68 + outpoint 36 + scriptCodeLen varint + scriptCode bytes). New `sign_btc_with_policy` entry takes a caller-supplied `priceMicrosPerSatoshi`, computes chain-derived `value_micros = sats * price`, emits a `BtcDecoded` event for audit, then delegates to soft `sign_gate::sign_with_policy` with the hard value (overriding the caller's claim).
- **Cap is on INPUT value, not output value.** BIP143 hashes outputs into `hashOutputs` so they're not directly recoverable from the preimage. Capping on input is conservative: input >= output (the diff is the fee). Matches how a BTC user thinks of "how much value am I authorizing chromatika to spend in this tx."
- **Move tests**: 14 cases at `move/chromatika-policy/tests/sign_gate_btc_test.move` — typical P2WPKH 1 BTC, dust, zero amount, max amount, P2WSH long scriptCode, 3-byte 0xfd-prefixed varint, truncated preimage abort (EPreimageTooShort), too-small preimage abort (EBadPreimage), price-conversion cases at $50k / $100k / dust / zero / saturation.
- **TS dispatch**: `policy-vault-sign.ts` `PolicySecpSignInput` extended with optional `btcHardPolicy: { priceMicrosPerSatoshi }`. Three-mode dispatch (EVM hard / BTC hard / soft) in priority order. `signBitcoinTxSighashPreimage` accepts new opts `isBtcTx?: boolean` + `priceMicrosPerSatoshi?: bigint`. `btc-send-native.ts` resolves BTC/USD via `getPrice('btc')` → `priceMicrosPerSatoshi` and passes through ONLY on the first sign call (multi-input txs would otherwise count N times against the cap).
- **Honesty model**: HARD on input value (decoded from on-chain preimage bytes); SOFT on price (caller-supplied; emitted on-chain via `BtcDecoded` event for auditability). Closes the BTC soft-policy gap in the original Policy Vault v0.

- **Spec target** - x402 v2.0 spec at `github.com/x402-foundation/x402`, `exact` scheme on Solana, USDC mint only (`EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v`). - **MV3 SW WASM data-URL workaround** - `vite` stays pinned at `8.0.3` exact (`8.0.9` and `8.0.10` were both retested and have a separate ESM `import.meta.url` regression, unrelated to this fix - retry on a future vite release). Independent root issue: chromium MV3 service workers can't construct a `URL` from the multi-MB `data:application/wasm;base64,…` blob that wasm-bindgen emits as the default fallback in `@ika.xyz/sdk`'s `dwallet_mpc_wasm.js` (the WASM blob is ~3.4 MB inlined). The error surfaces as `Failed to construct 'URL': Invalid base URL` deep inside `UserShareEncryptionKeys.fromRootSeedKey` and breaks every `createVault` onboarding path. Compounding it: `URL.createObjectURL` is **missing entirely** from the URL constructor in MV3 SW context (`'createObjectURL' in URL` returns `false` — the static method that MDN claims is available in service workers is genuinely absent in MV3), so the obvious "convert to blob URL" fix is impossible. Workaround landed in `src/background/service-worker-document-shim.ts`: intercept `new URL(...)` for the wasm data-URL prefix, decode the bytes into an in-SW stash keyed by a short id, return a synthetic `chrome-extension://<id>/__chromatika_wasm_stash__/<id>` URL, and patch global `fetch` to serve those bytes back as an `application/wasm` Response when the synthetic URL is fetched. Both shims are dormant for any other input. Drop the workaround when chromium gives MV3 SWs `URL.createObjectURL` back, OR when `@ika.xyz/sdk` ships its WASM as a separate `.wasm` asset.
