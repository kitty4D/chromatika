# EIP-1193 + EIP-6963 (EVM dapp injection)

EIP-1193 specifies the JavaScript provider interface every Ethereum dapp expects on `window.ethereum`. EIP-6963 (multi-injected provider discovery) lets multiple wallets coexist on the same page without clobbering `window.ethereum`. chromatika implements both - dapps see chromatika via either interface.

## EIP-1193 the interface

```ts
interface Eip1193Provider {
  request(args: { method: string, params?: any[] | object }): Promise<any>;
  on(event: 'accountsChanged' | 'chainChanged' | 'connect' | 'disconnect', cb: Function): void;
  removeListener(event: string, cb: Function): void;
}
```

key methods chromatika handles:
- `eth_requestAccounts` - opens connect approval popup, returns array of authorized addresses
- `eth_accounts` - returns currently authorized addresses (without prompting)
- `eth_chainId` - returns active EVM chain id (hex)
- `eth_sendTransaction` - opens TX_APPROVE popup, signs + broadcasts on approve
- `personal_sign` - opens sign popup, returns 65-byte hex signature
- `eth_signTypedData_v4` - opens sign popup, returns 65-byte hex signature
- `eth_call`, `eth_getBalance`, `eth_estimateGas`, `eth_getCode`, etc. - read-only RPCs pass through to the active EVM provider directly (no popup)
- `wallet_addEthereumChain` (EIP-3085) - see [eip-3085-3326.md](/library/tech/eip-3085-3326)
- `wallet_switchEthereumChain` (EIP-3326) - see [eip-3085-3326.md](/library/tech/eip-3085-3326)

events emitted:
- `connect` - on initial connection
- `disconnect` - on revoke / lock
- `accountsChanged` - when active dWallet for the origin changes
- `chainChanged` - when active EVM chain switches

## the page-script side (where the provider lives)

content script injects a page-script (`dapp-interface/inject.ts`) that runs in the page's JS world (not the isolated content-script world). this is the only context where:
- `window.ethereum` etc. can be set
- `dispatchEvent(new CustomEvent('eip6963:announceProvider', ...))` works
- the dapp's own JS can read / call our provider

the page-script communicates with the chromatika background via `window.postMessage` to the content-script, which forwards to background via `chrome.runtime.sendMessage`. round-trip: `dapp.window.ethereum.request(...)` → `postMessage(content_script)` → `sendMessage(background)` → chromatika handles → reverse path back.

## EIP-6963 multi-provider discovery

before EIP-6963, wallets fought over `window.ethereum` - last-injected wins, others get clobbered. now wallets announce themselves via custom events:

```ts
// chromatika announces itself
const eip6963ProviderInfo = {
  uuid: '<random uuid>',
  name: 'Chromatika',
  icon: 'data:image/svg+xml;base64,...',
  rdns: 'xyz.chromatika',
};

window.dispatchEvent(new CustomEvent('eip6963:announceProvider', {
  detail: Object.freeze({
    info: eip6963ProviderInfo,
    provider: chromatikaProvider,   // the EIP-1193 instance
  }),
}));

// also re-announce on dapp request
window.addEventListener('eip6963:requestProvider', () => {
  window.dispatchEvent(new CustomEvent('eip6963:announceProvider', { detail: ... }));
});
```

dapps that support EIP-6963 listen for `eip6963:announceProvider`, build a list of available providers, let the user pick. dapps that don't support EIP-6963 fall back to `window.ethereum` (chromatika still sets it for back-compat, but yields if another wallet was already there - polite coexistence).

## the per-origin permission model

connections are **per origin** + **per curve**:
- chromatika stores a permission record per origin in `chromatika_dapp_permissions_v1`
- each record has: `origin`, `selectedSecpDwalletId`, `selectedEd25519DwalletId`, `scopes`, `lastUsedAtMs`
- read methods (`eth_call`, `eth_getBalance`) are unauth (chain data, not user-private)
- write methods (`eth_requestAccounts`, `eth_sendTransaction`, `personal_sign`) require an active permission. without one, chromatika prompts via `eth_requestAccounts` flow

revocation: `revokeDappPermission({ origin })` drops the record. all subsequent write methods from that origin go back to needing approval.

## the bridge boundary

```
[dapp page world]
  window.ethereum.request({ method: 'eth_sendTransaction', params: [...] })

[page-script EIP-1193 wrapper]
  postMessage(window, { type: 'chromatika_dapp_request', method, params, requestId })

[content-script (isolated world)]
  on 'chromatika_dapp_request' message + verify event.source === window:
    chrome.runtime.sendMessage({ type: 'dapp_request', origin, method, params, requestId })

[background service worker]
  validate origin permission
  dispatch to handler (e.g. enqueueTxApproval for sendTransaction)
  → opens popup, awaits user
  → on approve, signs + broadcasts
  → returns result via chrome.runtime.sendMessage callback

[content-script]
  postMessage(window, { type: 'chromatika_dapp_response', requestId, result | error })

[page-script]
  resolve / reject the dapp's promise
```

per CLAUDE.md: bridge uses **`chrome.runtime.sendMessage` with origin + `event.source` validated**. content scripts validate that messages came from the page's own window (not an iframe spoofing a sibling page) before forwarding to background.

## what chromatika doesn't expose

- `eth_sign` (legacy raw signing) - dangerous (no domain separation), most dapps don't use it. chromatika rejects with "method not supported" rather than silently signing arbitrary bytes
- `eth_decrypt`, `eth_getEncryptionPublicKey` - the legacy MetaMask-only encryption surface. chromatika doesn't implement
- `wallet_watchAsset` (EIP-747) - asset management is in the wallet UI; not exposed to dapps for now
