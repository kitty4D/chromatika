# ika seed: Sui base + passkey (WebAuthn PRF)

vault `seedSource: 'passkey-prf'`, base chain `'sui'`. uses the WebAuthn PRF / HMAC-secret extension to produce a deterministic 32-byte secret on every assertion. that secret feeds **both** the unlock-envelope flow (see [passkey-prf-envelope.md](/library/tech/passkey-prf-envelope)) **and** the ika seed derivation - one PRF output, two purposes.

today this is a **Sui-only** path. Solana passkey vaults are not exposed (Lazor is a portal-mediated Solana passkey but uses recovery words for the seed, not PRF directly - see [ika-seed-solana-lazor.md](/library/tech/ika-seed-solana-lazor)).

## inputs

- `prfSecret`: 32-byte output from `webauthn.assertion.extensions.prf.results.first` (see [webauthn-prf-hmac-secret.md](/library/tech/webauthn-prf-hmac-secret))
- `prfSalt`: the per-vault 32-byte salt that was passed in `prf.eval.first` at register time and gets re-supplied on every assertion
- `encryption_key_index`: always `0`

note: the `prfSecret` is 32 bytes, **not** a sui ed25519 keypair. so the keccak preimage is **not** the `[scheme_flag || secret || index]` form used by mnemonic / private-key paths. it's a separate factory: `ikaRootSeedFromPasskeyPRF`.

## step-by-step

```
1. webauthn assertion
   navigator.credentials.get({
     publicKey: {
       challenge: random32,
       rpId: envelope.rpId,
       allowCredentials: [{ id: decode(envelope.credentialIdB64Url), type: 'public-key' }],
       extensions: { prf: { eval: { first: envelope.prfSaltB64_decoded } } }
     }
   })

2. extract PRF result
   prfSecret = response.clientExtensionResults.prf.results.first   // 32 bytes

3. assemble keccak preimage
   indexLe = u32_le(0)
   preimage = prfSecret || indexLe   // 36 bytes total

4. hash
   seed_32 = keccak256(preimage)

5. derive both curves
   uskSecp = UserShareEncryptionKeys.fromRootSeedKey(seed_32, Curve.SECP256K1)
   uskEd25519 = UserShareEncryptionKeys.fromRootSeedKey(seed_32, Curve.ED25519)

6. zero seed_32 and prfSecret
```

## what gets stored

- `record.passkeyCredentialId`: webauthn `credential.rawId` in base64url (RFC 4648 §5)
- `record.passkeyPublicKeyB64`: 33-byte compressed secp256r1 public key from `attestationObject` parse
- `record.passkeyRpId`: the relying-party id (chrome-extension origin)
- `record.passkeyPrfSaltB64`: the 32-byte salt the wallet generated at register time and **must** re-supply on every assertion
- `record.ikaShareKeysB64`: serialized USK bytes for both curves
- `record.mnemonic`, `suiPrivateKeyBech32`: not present
- the `prfSecret` is **never stored** - it's regenerated by the authenticator on every assertion

## the fee-payer problem

passkey vaults don't have a sui ed25519 fee-payer keypair derived locally - the passkey produces a secp256r1 signature, not an ed25519 sui keypair. so:

- ika seed: derived from `prfSecret` via `ikaRootSeedFromPasskeyPRF` - works fine
- fee-payer for Sui PTB ops (DKG, presign, sign, sendSuiNative): there's **no local sui keypair** to sign with

per the agent's exploration, `feeMaterialFromVaultRecord` on a passkey vault **throws** today - which means PTB-based ika operations on a Sui-passkey vault need a different fee-funding path. this might use the passkey-derived address (Sui SIP-9 passkey addresses are valid Sui addresses with flag `0x06`) and dispatch the actual signing through the passkey assertion popup.

practical implication: if you're driving a Sui-passkey vault via `createDWallet`, the wallet should pop a passkey-sign popup for each fee-paying PTB. the design tradeoff is "no software-held sui key = more popup interactions". this matches the user's mental model of "passkey = hardware-rooted security".

## restore on a new device

```
1. user re-registers the same passkey on a new chromatika install
   - if the passkey is platform-bound (Touch ID), they must use the same physical device
   - if the passkey is roaming (yubikey) or synced (iCloud Passwords / Google Passkey), it works on any device
2. addVaultPasskey or createPasskeyVault re-creates the envelope with the same credentialId
3. assertion produces the same prfSecret given the same (credential, prfSalt) pair (per WebAuthn PRF spec determinism)
4. ika seed = keccak256(prfSecret || index_le) - identical
5. discoverDWallets reattaches existing dWallets owned by this identity
```

determinism guaranteed by:
- WebAuthn PRF / HMAC-secret spec: same credential + same salt + same operation = same output
- credential public key is part of the PRF input behind the scenes, so even if two credentials shared the same salt, they'd produce different outputs
- chromatika persists `prfSaltB64` in the vault - same salt on restore = same PRF output

## what doesn't work

- **non-PRF authenticators**: some older passkey authenticators don't expose the PRF / HMAC-secret extension. chromatika **rejects** registration on those - no way to deterministically seed the ika identity. surface a clear error suggesting a different authenticator
- **lost passkey**: if the user loses all their passkey credentials and didn't register a recovery-words branch, the vault is unrecoverable. recovery words are an envelope-level fallback (see [recovery-words-envelope.md](/library/tech/recovery-words-envelope)); they unlock the vault but the **ika identity** still requires one of the registered seeds. for passkey vaults, the recovery-words branch has to either re-derive the same prfSecret somehow (impossible - it's authenticator-bound) or store the USK bytes separately so they can be re-loaded after recovery-words-only unlock. CLAUDE.md notes the recovery-words envelope unlocks the vault, after which the user usually re-registers a fresh primary credential
- **cross-curve identity reuse**: same passkey, same salt, different chromatika install = same ika seed = same dWallet. but two different passkey vaults on the same install with **different salts** = different identities even if it's the same authenticator

## the fee-payer "throws today" workaround

in practice, Sui-passkey vaults are an emerging surface. the canonical implementation either:
- pops the passkey assertion to sign each Sui PTB (slow but secure)
- pre-derives a sui ed25519 fee-payer keypair from the prfSecret (`prfSecret` → `ikaRootSeedFromPasskeyPRF` produces the ika seed; a separate keccak with a different domain tag could produce a sui keypair seed, but this isn't the current implementation)
- uses passkey-derived addresses for ika operations once ika supports passkey-anchored fee payment

for now, treat Sui-passkey vaults as "ika identity works, gas funding requires more thought" - check the current code path before relying on it for production flows.
