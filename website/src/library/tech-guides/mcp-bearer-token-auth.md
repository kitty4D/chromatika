# MCP bearer-token auth

every chromatika install gets a per-install random bearer token used to gate the localhost HTTP MCP listener. the token rotates on demand, persists in extension storage, and is pushed to the native host via the `{ type: 'config', tokenHex }` native messaging frame. agent clients pass it as `Authorization: Bearer <tokenHex>` on every HTTP request.

## token format

```
tokenHex = hex(crypto.getRandomValues(Uint8Array(32)))
        = 64-char hex string (256 bits of randomness)
```

256 bits is overkill for offline brute-force resistance but cheap to generate. the token never leaves the local machine - it's not exposed to the internet, not signed over, not used for cryptographic protocols. it's a simple shared secret between chromatika and any local agent process the user has authorized.

## storage

```jsonc
chrome.storage.local["chromatika_mcp_v1"] = {
  "enabled": true,
  "tokenHex": "abc...64chars...",
  "listenPort": 54321,
  "listenHost": "127.0.0.1",
  "nativeHostName": "com.chromatika.mcp_host",
  "desiredListenPort": null   // user-supplied stable port, or null for random
}
```

`chromatika_mcp_v1` lives in `chrome.storage.local`. cleared on uninstall. surface for read / write:
- `mcpStatus` - returns the whole record (or sanitized subset)
- `mcpEnable` / `mcpDisable` - toggles `enabled`
- `mcpRotateToken` - generates a fresh `tokenHex`, pushes to running host
- `mcpSetDesiredPort` - sets `desiredListenPort`, triggers a `reconfigure-port` frame to the host

## generation

```ts
async function generateToken() {
  const buf = new Uint8Array(32);
  crypto.getRandomValues(buf);
  return [...buf].map(b => b.toString(16).padStart(2, '0')).join('');
}
```

generated by chromatika at:
- first `mcpEnable` if `tokenHex` is empty / null
- explicit `mcpRotateToken` call

## the push to host

on `chrome.runtime.connectNative`, chromatika pushes `{ type: 'config', tokenHex }` as the **first native messaging frame**. the host stores it in memory:

```js
const STATE = { tokenHex: null };

function handleMessage(msg) {
  if (msg.type === 'config') {
    STATE.tokenHex = msg.tokenHex;
    sendFrame({ ok: true, kind: 'config-ack', hasToken: STATE.tokenHex != null });
    return;
  }
  // ... other frame handling
}
```

the token is **never persisted on disk by the host** - only held in process memory. if the host process is killed and respawned, chromatika reconnects and pushes the token again.

## validation on HTTP requests

```js
function httpHandler(req, res) {
  const auth = req.headers['authorization'] ?? '';
  const expected = STATE.tokenHex ? `Bearer ${STATE.tokenHex}` : null;

  if (!expected || auth !== expected) {
    res.statusCode = 401;
    res.setHeader('Content-Type', 'application/json');
    res.end(JSON.stringify({
      jsonrpc: '2.0',
      id: null,
      error: { code: -32001, message: 'unauthorized' }
    }));
    return;
  }

  // ... proceed to JSON-RPC handling
}
```

constant-time comparison would be ideal here (defends against timing attacks). chromatika's host uses string equality which is **technically** non-constant-time but the threat is moot for localhost: an attacker who can time HTTP responses to localhost has already won (they can read storage, etc.). for paranoia, swap to `crypto.timingSafeEqual(Buffer.from(actual), Buffer.from(expected))`.

## rotation

```ts
async function rotateToken() {
  const newToken = await generateToken();
  await chrome.storage.local.set({
    chromatika_mcp_v1: { ...current, tokenHex: newToken }
  });
  if (nativePort) {
    nativePort.postMessage({ type: 'config', tokenHex: newToken });
    // host overwrites STATE.tokenHex; old token immediately invalid for new requests
  }
}
```

rotation is **immediate** for new requests - the host's `STATE.tokenHex` updates as soon as the config frame arrives. existing in-flight requests with the old token complete normally (they passed validation when they arrived). new requests with the old token return 401.

agent clients (Claude Desktop, Cursor) need to update their config with the new token. this is manual today; tracked future is some kind of token-broker handshake.

## per-install scoping

each chromatika install (each browser profile, each computer) generates its own token. the token is **not** synced across devices - chromatika doesn't write it to `chrome.storage.sync`. this is intentional: each install has its own MCP listener with its own port, its own host process, its own token. cross-device usage requires the user to grab the per-install URL + token and paste into their agent client config on each machine.

## attack model

| threat | mitigation |
|--------|-----------|
| internet attacker hits `http://my-public-ip:port/mcp` | listener bound to 127.0.0.1; not externally reachable |
| local attacker (same machine, same user) reads `chrome.storage.local` | they have the token. but they can also read your vault directly. game over at this layer |
| local attacker (different user on same machine) | OS file permissions on chrome's data dir prevent cross-user reads. attacker would need privesc |
| MITM between agent client and HTTP listener | localhost loopback. no MITM possible without local malware (which already wins) |
| browser-based attack (web page tries to reach localhost) | browsers block fetch to localhost without CORS; the listener doesn't set CORS headers. fails |
| token leak via screenshot / shoulder-surf | rotate the token via `mcpRotateToken`. takes effect immediately |

bottom line: bearer token + localhost binding gives "this requires a process on your machine that you've authorized" - not "this is encrypted in transit and authenticated cryptographically". that's the right model for local MCP.

## reveal in the UI

`AgentsSettingsSection` exposes:
- copy token to clipboard (one click)
- reveal token (click to show, hidden by default)
- rotate (button, generates fresh)
- copy agent URL (`http://127.0.0.1:<port>/mcp`)

the token is **not** masked in the underlying tRPC response (`mcpStatus` returns it in the clear) - the UI handles masking. agents reading via tRPC see the actual token.

## library

- `crypto.getRandomValues` (browser native) for generation
- `chrome.storage.local` for persistence
- `port.postMessage({ type: 'config', tokenHex })` for the push
- internal: `mcp-storage.ts` for storage shape + helpers
- internal: `mcp-auth.ts` (with `mcp-auth.test.ts`) for the validation logic on the host side
