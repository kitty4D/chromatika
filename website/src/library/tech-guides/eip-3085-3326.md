# EIP-3085 (`wallet_addEthereumChain`) + EIP-3326 (`wallet_switchEthereumChain`)

these two EIPs let dapps suggest networks: "hey, my dapp is on Polygon - if you don't have Polygon, here are the parameters; if you do, please switch to it." chromatika implements both with user approval.

## `wallet_switchEthereumChain` (EIP-3326)

dapp asks chromatika to switch to a specific chain id:

```ts
await window.ethereum.request({
  method: "wallet_switchEthereumChain",
  params: [{ chainId: "0x89" }], // hex chain id, e.g. 137 for Polygon
});
```

chromatika handler:

```
1. parse chainId from hex (0x89 → 137)
2. look up the chain in registry (built-in + custom networks)
3. if not in registry:
   - throw error code 4902 ("unrecognized chain id; use wallet_addEthereumChain to add it")
4. if in registry but not active:
   - open a small "switch chain?" approval popup with chain name + RPC
   - on user approve: setActiveEvm(chainId), emit 'chainChanged' event
   - on user reject: throw error code 4001 ("user rejected the request")
5. if already active:
   - return null (per EIP-3326 spec, success is null result)
```

## `wallet_addEthereumChain` (EIP-3085)

dapp asks chromatika to add a custom network:

```ts
await window.ethereum.request({
  method: "wallet_addEthereumChain",
  params: [
    {
      chainId: "0xa4b1",
      chainName: "Arbitrum One",
      nativeCurrency: { name: "Ether", symbol: "ETH", decimals: 18 },
      rpcUrls: ["https://arb1.arbitrum.io/rpc"],
      blockExplorerUrls: ["https://arbiscan.io"],
      iconUrls: ["data:image/svg+xml;base64,..."],
    },
  ],
});
```

chromatika handler:

```
1. parse + validate parameters
   - chainId is hex
   - rpcUrls[0] is a valid HTTPS URL
   - nativeCurrency has decimals=18 (uncommon to differ; chromatika rejects non-18 today)
   - blockExplorerUrls is optional but recommended
2. validate the RPC by sending eth_chainId probe:
   - if response.chainId !== params.chainId, reject (RPC lies about its chain)
3. check if chain already exists:
   - in built-in registry? say "already supported, switching to it" (user still confirms)
   - in custom registry? same
   - new? proceed to step 4
4. open approval popup with the proposed chain details
5. on user approve:
   - addCustomNetwork(params)
   - setActiveEvm(chainId)
   - emit 'chainChanged' event
6. on user reject: throw 4001
```

## the EIP-3085 abuse vector

a dapp could submit a custom RPC that lies about its chain id, then once active intercept all the user's tx + read calls. chromatika defends with:

- **chain id verification**: probe the RPC's `eth_chainId` first; reject mismatch
- **user approval**: every add-chain requires explicit consent, not silent acceptance
- **explorer URL display**: the popup shows the explorer URL so the user can sanity-check
- **default RPC for known chains**: if the dapp suggests adding a chain id that matches a built-in (e.g. mainnet ethereum), chromatika prefers the built-in RPC over the dapp-suggested one

## the chain registry

chromatika ships built-in entries for major chains (Ethereum, Polygon, Arbitrum, Optimism, Base, BNB, etc.) plus several testnets. dapps can add custom chains via this EIP-3085 flow, or users can add via the chromatika UI (or via Chainlist search; see [manage-networks.md](/library/user/manage-networks)).

custom chains live in `chromatika_custom_networks_v1` storage. removing a chain that's currently active falls back to a default.

## the active-tier vs vault-tier distinction

EIP-3085 / EIP-3326 only deal with the **EVM** active chain, which is a single chain id. Sui and Solana have a more complex "vault-tier" + "dWallet-tier" model (e.g. dWallet on Sui mainnet but vault running ops on Sui testnet briefly). EVM doesn't have that today - one active chain at a time.

if a dapp wanted analogous Sui / Solana network management, that's not EIP-3085's scope. Wallet Standard (Sui + Solana) has its own `wallet:setNetwork` style features but chromatika exposes those through different surfaces.

## edge cases

- **chain id changes mid-session**: technically possible if a dapp switches via EIP-3326 then submits a tx that targets a different chain. chromatika checks tx `chainId` matches active EVM chain at sign time; mismatch rejects with a clear error
- **chain id collision**: two custom chains with the same chain id is impossible (chain id is the registry key). adding a new custom that shadows a built-in chain id is also blocked - built-ins win
- **RPC unreachable after add**: the eth_chainId probe verifies the RPC works **at add time**. if the RPC dies later, that's a `getEvmRpcHealth` issue (separately surfaced)
